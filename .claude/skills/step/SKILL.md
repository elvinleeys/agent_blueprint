# 단계 진행 매뉴얼 (/step)

이번에 받은 단계: `$ARGUMENTS`

계획표의 단계 하나를 끝까지 진행한다. 각 칸마다 아래 순서를 지킨다. push는 절대 하지 않는다.

## 0. 시작 점검
- `tasks/spec-*.md`에서 스펙 문서를 찾는다(여러 개면 어느 것인지 묻는다). 계획표는 "계획(단계 → 커밋)" 표다.
- `git branch --show-current`와 `git status --short`를 확인한다. `main`이면 멈추고 브랜치부터 만들자고 말한다. 이번 단계와 무관한 미커밋 변경이 있으면 알린다(`docs/prompts.md`는 정상).
- `CLAUDE.md`와 스펙 문서를 읽고, 코드 질문은 graphify 규칙(`graphify query`)을 먼저 따른다.

## 1. 단계 고르기와 말하기
- 인자가 있으면 그 단계, 없으면 단계 칸에 `✅`가 없는 첫 단계를 고른다. 인자로 준 단계가 이미 `✅`면 그렇게 알리고 다시 할지 묻는다.
- 사용자에게 먼저 말한다: 단계 이름, 내용, 계획표의 검증 방법, 커밋 메시지, 화면을 바꾸는 단계인지, 시험 데이터가 먼저 필요한지. 사용자가 진행하라고 하면 시작한다.

## 2. 시험 데이터와 기대 결과 먼저 (필요한 단계만)
- 새 판정·출력 동작을 만드는 단계면, 구현 전에 `fixtures/`의 시험 데이터와 기대 결과 표를 만들어 **보여 주고 승인받는다**. 승인 전에는 구현을 시작하지 않는다. 이미 승인된 시험 데이터가 있으면 그렇다고 말하고 넘어간다.

## 3. 구현 (CLAUDE.md 규칙)
- 파일은 `Write`·`Edit`으로만 만든다. 셸 heredoc(`<<`)로 파일을 쓰지 않는다.
- **먼저 사용자에게 묻는다**: 새 패키지 추가, DB 마이그레이션·스키마 변경, 기존 어댑터 파일 수정, 업로드 한도 변경.
- 실제 OpenAI 호출(`npm run test:draft` 포함)과 DB 쓰기를 하지 않는다. AI 테스트는 가짜 클라이언트로 한다.
- 폴더 책임을 지킨다(`core/`는 React·Next import 금지, `app/`에는 라우팅 파일만 등).
- 서버가 필요하면 3000번만 쓴다(사용자가 켠 서버는 끄지 않는다).
- 코드를 바꿨으면 `graphify update .`를 돌려 그래프를 갱신한다.
- 직원을 부르기 전에 스스로 `npx tsc --noEmit`을 먼저 통과시킨다.

## 4. 직원 검사 (순서 고정)
1. **verifier**(검증담당직원): 단계 이름, 기준 커밋, 이전 테스트 개수를 알려 주고 부른다.
2. **spec-checker**(스펙검수직원): 스펙 문서 경로, 단계 이름, 기준 커밋, verifier 보고서를 함께 넘긴다.
3. **ui-reviewer**(화면검사직원): 이번 변경에 `components/`(`ui/` 제외)나 `app/`의 화면 파일이 있을 때만 부른다. 검사할 파일 목록을 넘긴다.

직원을 부를 수 없으면(목록에 없음) 멈추고 사용자에게 알린다. 직원 일을 내가 대신해서 통과시키지 않는다.

## 5. 문제 처리
- 직원이 문제(⚠️·❌, 불일치, 보류, 높음·보통 문제)를 말하면 내가 고친다. 직원은 고치지 않는다.
- 고친 뒤 **그 문제를 말한 직원**에게 다시 검사받는다. 같은 직원에게 **재검사는 최대 2번**까지다. 3번째 검사에서도 문제가 남으면 멈추고 사용자에게 무엇이 안 되는지·시도한 것·선택지를 말하고 묻는다.
- 코드를 고쳤고 문제를 말한 직원이 verifier가 아니면, 고친 코드가 기준 결과를 깨지 않았는지 verifier도 한 번 더 부른다(이 호출은 재시도 횟수에 세지 않는다).
- spec-checker가 **조건부 완료**를 주면 조건(사용자가 확인할 것)을 사용자에게 그대로 말하고, 사용자가 받아들일 때만 진행한다. 조건은 PR 메시지에 적는다.

## 6. 테스트 기대값을 바꿔야 할 때
- 기대 결과(`expected.json`·`expected.md`)나 테스트의 기대값을 바꾸기 **전에** 무엇을, 왜 바꾸는지 사용자에게 보고하고 승인받는다. 테스트를 통과시키려고 기준을 고치지 않는다. 틀린 쪽이 코드면 코드를 고친다.

## 7. 커밋과 완료 표시
- `npx tsc --noEmit`을 먼저 통과시킨 뒤 커밋한다.
- `git add`는 파일 이름을 하나씩 적는다(`.`·`-A` 금지, `docs/prompts.md` 제외). 커밋 메시지는 계획표의 커밋 칸 접두사(`feat:` 등)를 쓴다. 설계도 스키마 변경은 별도 커밋이다. 메시지 끝에 시스템이 알려 준 Co-Authored-By 줄을 붙인다.
- 구현 커밋 뒤에, 계획표의 그 단계 칸 앞에 `✅`를 붙이는 변경을 별도 `docs:` 커밋으로 남긴다.
- **`git push`는 하지 않는다.** 대신 PR 메시지를 제안한다: 제목, 변경 요약, 검증 결과(직원별), 확인 못 함·조건, 사용자가 직접 할 일.
