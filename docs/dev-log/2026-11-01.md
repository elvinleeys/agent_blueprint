## 1. 저장 큐 `drain()` (1단계)

`SaveQueue.settle()`은 보내지 않은 값을 버린다(초안 다시 생성용). 내보내기에는 쓸 수 없어서 `drain(): Promise<boolean>`을 더했다. 대기·전송 중·그 사이 들어온 편집을 모두 보내고 끝나면 true, 전송이 실패하면 false이고 실패한 값은 남아 `retry`할 수 있다. `drain` 시작 때 이미 실패해 있던 값은 한 번만 다시 보내고, `drain` 중에 새로 실패한 값은 다시 보내지 않는다. 처음 구현은 새로 실패한 값을 한 번 더 보내는 버그가 있었고 실패 테스트가 잡았다.

### 기준 파일 검토에서 정한 사항

- **입력:** 기준 파일은 현재 스펙으로 만든 사전 테스트 응답(`tasks/draft-outputs/2026-10-29T09-08-49-165Z/…terra-1.json`)을 입력으로 쓴다. 스펙 파일의 마지막 수정(17:55) 이후에 만든 응답이라 스펙과 설계도가 같은 화면을 말한다. Tailwind 변형은 같은 설계도에서 스택만 바꾸고 FSD를 유지해 디렉토리와 위치가 맞게 했다. React 변형은 React·CSS Modules·유형 중심으로 바꾸고 페이지의 `params: Promise<…>`(Next.js 전용)를 빼서 `props: 없음`으로 뒀다.
- **기준 파일 5개**(`fixtures/prompts/`): `product-detail/{prompt,rule-file}.md`, `product-detail-tailwind/rule-file.md`, `product-detail-react/{prompt,rule-file}.md`. 파일이 없으면 만들고 그 실행을 실패시키는 방식이라, 내용은 사람이 검토한 뒤에 커밋한다.
- **구현 순서:** FSD는 아래 계층부터(shared → entities → features → widgets → pages → app), 그 외는 트리의 말단부터 부모 순서. Next.js는 끝에 라우팅 파일, React는 끝에 "라우터에 페이지 연결". 문장은 "하위 컴포넌트와 훅을 먼저 구현하고, 이를 사용하는 상위 컴포넌트를 나중에 구현한다"와 "각 단계가 끝나면 타입과 import 관계를 확인하고, 전체 구현이 끝나면 프로젝트의 타입 검사 스크립트를 실행한다".
- **예외 상태:** 로딩·오류 같은 예외 상태는 기존 프로젝트의 공통 처리를 쓰고, 없으면 임의로 정하지 않고 완료 보고에 기록한다. 규칙 파일에 인터랙션·예외 기준이 있으면 따르고, 없는 것은 확인 사항에 기록한다.
- **Server·Client 규칙:** Server·Client 판단, Client 모듈 포함, children 전달, 조회 데이터 props 전달을 쓰고, "설계도에서 client 노드 아래 노드는 그 client 파일이 가져오는 컴포넌트다. Server로 유지할 UI는 server 부모 아래 두고 구현 때 children으로 넘긴다"를 함께 적어 NX-04와 모순되지 않게 했다.
- **자동 표시:** 노드의 "서버 통신(조회·요청)"(예전 "데이터 조회"), 상태 소유 요약, 훅이 있으면 "사용하는 훅", 훅에는 "사용 위치(부모 이름과 렌더링 방식)", 책임이 둘 이상이면 목록. 서버 통신 노드가 페이지 하나뿐이면 "같은 데이터는 페이지에서 조회한 값을 전달한다…" 규칙을 넣는다. 설계도의 값은 생성기가 바꾸지 않는다.
- **토큰:** Tailwind·CSS Modules 모두 "기존 테마(또는 CSS 변수)에 있으면 그대로, 없으면 임의 값을 만들지 않고 보고, 사용자가 확정한 경우에만 정의". 스펙에 없는데 설계도에서 쓰인 토큰은 "정의가 필요한 토큰"으로 모은다. 클래스로 바꿀 수 없는 토큰(예: `layout.maxWidth`)은 표 대신 "프로젝트 테마에 정의된 토큰을 사용한다, 없으면 임의의 클래스를 만들지 않고 보고한다" 문장으로 적는다.
- **Tailwind:** 버전은 스택에 두지 않고 문장으로 대응(4는 `@theme`, 3은 `tailwind.config`의 `theme.extend`). 토큰 → 클래스 대응표에서 간격은 기본 단위(4px)를 가정한다고 밝힌다. 반응형은 미리보기의 `resolveLayout`을 재사용해 모바일 우선(`md:`=태블릿, `lg:`=데스크톱)으로 바꾼다(미리보기와 같은 배치를 말하도록 `Breakpoint`에 tablet을 열었다). 배치 섹션에는 grid·flex·간격·정렬·반응형·차지 칸 클래스만, 스타일 섹션에는 색·모서리 같은 시각 클래스만 둬서 반복하지 않는다. `padding`·`margin`은 스타일 쪽에 뒀다.
- **React:** 화면 주소를 라우터 형식으로 바꾸고(`/products/[id]` → `/products/:id`, `[...x]`는 `*`), 라우팅 규칙("기존 라우팅 라이브러리를 따른다, `<페이지>`를 `<주소>`에 연결한다, 기존 라우터가 없으면 임의로 설치·선택하지 않고 보고")과 데이터 로딩 규칙을 넣고, "모든 컴포넌트는 브라우저에서 실행된다"를 스택 규칙에 쓴다. 렌더링 방식 표기는 쓰지 않는다. 노드의 props가 없으면 "props: 없음"(훅 제외)으로 적는다.
- **FSD 빈 pages 폴더:** 기존 프로젝트면 라우터 구성(App Router 여부, 기존 pages 폴더)을 먼저 확인하고 충돌하면 보고한다. 대안으로 FSD pages 계층 이름을 `views`로 바꾸는 방법이 있음을 함께 적는다(보고 후 결정).
- **`paths` 머리말:** FSD는 슬라이스 폴더 단위(`src/widgets/product-info/ui/**`), 유형·기능 중심은 노드의 파일 경로를 하나씩 적는다. `components/`·`hooks/` 같은 공용 폴더를 통째로 적으면 다른 화면 작업에도 규칙이 적용되기 때문이다. Next.js는 라우팅 파일도 넣고, 라우트의 `[id]`는 glob에서 글자 모임으로 읽히므로 `*`로 바꾼다(`[...x]`는 `**`). 같은 값은 한 번, 정렬.
- **파일 이름:** 지시서가 가리키는 경로(`.claude/rules/product-detail.md`)와 내려받기 이름은 같은 함수에서 나오고 테스트로 고정했다. 이름은 한국어 화면 이름이 아니라 루트 노드 이름(영문 PascalCase)에서 끝의 `Page`를 빼고 kebab-case로 만든다. 비면 `screen`. 같은 루트 이름의 화면이 둘이면 이름이 겹친다(알려진 한계).

### 검사 규칙·자동 보정

- **NX-05(경고):** FSD가 아닌 Next.js에서 파일 위치가 `pages/` 또는 `app/`으로 시작하면 Next.js 라우팅 폴더와 겹칠 수 있다는 경고. `CLAUDE.md`와 `data-model.md`의 규칙 표에 반영했다.
- **Tailwind 자동 보정:** 스택이 Tailwind인데 노드 `style.scope`가 `module`이면 `normalizeBlueprint`가 `utility`로 바꾸고 보정 내역에 기록한다.

## 발생한 문제와 해결

- `settle`을 내보내기에 쓸 수 없다는 것을 코드를 읽고 확인해서 `drain`을 새로 만들었다. 요청서에는 없던 발견이다.
- 기준 파일 입력이 처음에는 예전 샘플 설계도와 새 스펙 문장을 섞어 어긋났다. 위 입력으로 교체했다.
- 셸 명령에 빈 heredoc을 두 번 실행해 프로젝트 규칙(heredoc 금지)을 어겼다(파일은 바뀌지 않음). 7단계의 훅으로 막는다.
- PostToolUse 훅이 `tsc` 실패를 여러 번 알렸지만 직접 다시 실행하면 오류가 없었다. 원인은 확인 못 함(편집 중간 상태였을 가능성).

## 알려진 한계

- `paths` glob이 실제 Claude Code에서 도는지는 열어 보지 못했다(문서에 맞춰 쓴 것).
- 토큰 인식은 `color`·`spacing`·`radius`·`layout`·`font`·`shadow`·`size`·`border`·`opacity` 접두사만 한다. 클래스로 바꾸는 것은 색·간격·모서리뿐이다.
- 기준 파일은 AI 응답 1건 기준이라 가정한 필드(`assumedFields`)가 있는 입력의 기준 파일은 없다(단위 테스트로만 확인).
- 같은 루트 이름의 화면이 둘이면 규칙 파일 이름이 겹친다.
