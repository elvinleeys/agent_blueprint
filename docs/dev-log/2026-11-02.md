## 정한 사항

- **내보내기는 DB에 저장된 최신 판만 쓴다.** 그래서 화면이 먼저 저장 큐를 `drain()`하고, 실패하면 요청하지 않는다(`runExport`, 테스트로 고정). 지시서 기록으로 최신 판이 연결되면 그다음 편집은 새 판으로 저장된다. 새 판 만들기는 내보내기 라우트가 하지 않고 다음 편집의 `saveBlueprint`가 한다.
- **같은 내용이면 기록만 건너뛴다.** 같은 판·같은 형식의 직전 기록과 비교한다. 복사·내려받기는 몇 번이든 된다.
- **스펙이 비었다는 경고는 서버가 판단한다**(`specEmpty`). 서버가 쓰는 것은 저장된 스펙 입력이고, 화면의 입력칸 값과 다를 수 있기 때문이다. 그래서 경고는 내보낸 뒤 결과 위에 보인다.
- **화면 주소 안내는 설계도의 `stack.framework`로 정한다**(Next.js: 페이지 파일 위치 / React: 라우터 경로, `:id` 변환 / HTML: 파일 경로 참고용). 구조 설계 탭의 입력칸 도움말은 아직 Next.js 문구 그대로다.
- **HTML은 숨기지 않고 "실험적"으로 표시했다.** 숨기면 이미 만든 HTML 프로젝트와 어긋나고, 표시는 선택은 막지 않으면서 전용 검사 규칙이 없다는 것을 알린다.
- **프로젝트 삭제는 DB 연쇄 삭제를 쓴다.** 앱에서 다른 표를 따로 지우지 않는다. 이름 재입력 확인은 화면만 하고 서버는 소유(RLS)만 확인한다. 삭제 뒤 목록으로 이동한다.
- 주소 저장은 upsert로 하지 않는다. 기존 `saveSpecInput`의 upsert는 7개 항목과 이미지 수를 덮어쓰므로, route만 update하고 행이 없을 때만 빈 스펙으로 insert한다.

## 발생한 문제와 해결

- 내가 빈 python heredoc을 실행해 명령이 멈췄고, 테스트 코드를 `cat >> <<EOF`로 길게 붙이기도 했다(프로젝트 규칙 위반). 7단계 훅을 붙인 뒤 같은 실수는 훅이 실행 전에 막았다(이 훅이 실제 세션에서 내 명령을 막은 것을 확인).
- `ExportOutcome`의 `kind`가 실패 이유의 `kind`와 겹쳐 타입이 맞지 않아 실패 이유를 `reason`으로 바꿨다.
- 서버 오류 본문은 `{ error: { code, message } }`인데 처음에는 `error`를 문자열로 읽었다. 테스트가 아니라 코드를 다시 읽다가 고쳤다.
- PostToolUse `tsc` 훅이 편집 중간 상태에서 실패를 알렸지만 직접 다시 실행하면 통과했다(이전과 같은 현상).

## 알려진 한계

- 경쟁 상태는 처리하지 않았다: `saveSpecRoute`(행이 없을 때 동시 호출), `saveBlueprint`(지시서 연결 확인과 쓰기 사이), 내보내기(비교와 기록 사이, 최신 판 id 읽기와 설계도 읽기 사이).
- `prompt_exports`·프로젝트 삭제의 RLS·연쇄 삭제는 실제 Supabase에서 확인하지 못했다(가짜 DB 테스트만). 사용자가 화면에서 확인한다.
- 지시서 탭과 설정 탭의 클릭 흐름(복사, 확인 창, 삭제)은 서버 렌더링 스모크 테스트로 볼 수 없어 브라우저 확인이 필요하다. 설정 탭은 `useRouter` 때문에 렌더링 테스트도 없다.
- 구조 설계 탭의 화면 주소 입력칸 도움말은 스택별로 바꾸지 않았다.
- `paths` glob이 실제 Claude Code에서 도는지는 열어 보지 못했다.
