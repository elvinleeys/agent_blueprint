# 구현 검사: 설계 → 지시 → 구현 → 검증

브랜치 `feat/implementation-check` → `main`. 스펙과 단계별 기록은 `tasks/spec-implementation-check.md`.

## 무엇을 왜 만들었나

AgentBlueprint는 화면 구조를 설계도로 만들고, 그 설계도를 AI 에이전트용 지시서로 내보낸다. 지금까지는 **에이전트가 지시서대로 만들었는지 확인할 방법이 없었다.** 이 PR은 그 마지막 고리를 채워 "설계 → 지시 → 구현 → 검증" 순환을 닫는다.

- **검증**: 에이전트가 만든 코드(폴더 업로드 또는 GitHub 공개 저장소)를, 지시서를 내보낸 판의 설계도와 비교한다.
- **판정은 코드가 한다**: 노드와 코드 컴포넌트의 짝, 렌더링 관계, 상태·props·이벤트·서버 통신, 파일 위치, 스택 규칙(Next.js·React·Tailwind·FSD)을 `core/impl-check`가 판정한다. 같은 입력이면 같은 결과다.
- **AI는 의견만 낸다**: 코드로 확신할 수 없는 것(짝이 맞는지, 책임을 수행하는지)만 AI가 제안하고, 설계 준수 숫자에는 넣지 않는다. 최종 결정은 사람이 한다.
- **다시 지시로**: 확실한 항목과 사용자가 포함한 항목으로 **수정 지시서**를 만든다(템플릿, AI 없음). 에이전트에게 다시 넘기면 순환이 이어진다.
- **채점 스크립트**: 화면·DB·AI 없이 터미널에서 같은 판정을 숫자로 내어(`npm run score`), 지시서를 바꿨을 때 구현 품질이 어떻게 달라지는지 비교할 수 있다.

## 알려진 한계

스펙 위험 목록에서 "PR 설명에 반드시 적는다"로 표시한 것(③·⑤·⑦·⑧):

1. **CSS·CSS Modules는 배치·토큰을 코드로 판정하지 않는다.** CSS 파일을 읽지 않으므로 노드마다 "확인 필요" 1건으로 보낸다. Tailwind만 클래스로 판정한다.
2. **`_`·`-`만 다른 이름(짝짓기 D3)의 시험 범위가 좁다.** 설계도 노드 이름은 PascalCase만 허용해 `_`·`-`가 든 노드 이름을 입력할 수 없다. 그래서 이 규칙은 이름 유사도 계산(`Product_Gallery`↔`ProductGallery`가 1.00)과 파일 이름(`product-gallery.tsx`)에서 가져온 이름을 비교하는 수준으로만 시험했다.
3. **확정한 짝은 저장하지 않는다.** "같은 것으로 짝짓기"와 "AI 제안 받아들이기"로 확정한 짝은 화면 안에서만 기억한다. 작업공간을 떠났다 오거나 새로고침한 뒤 새로 검사하면 같은 노드가 다시 확인 필요로 나온다.
4. **확정한 짝의 이름 차이는 수정 지시서에 들어가지 않는다.** 확정한 짝은 확실한 짝으로 판정되므로, 설계 이름(예: ProductGallery)과 코드 이름(예: ItemImages)이 달라도 "이름을 설계대로 맞춘다"는 항목이 생기지 않는다. 확인 필요 카드로 남아 있을 때만 할 일에 이름·import 변경이 들어간다.

그 밖에 알고 있는 것: 렌더링 관계는 정적 분석이라 `React.lazy`·동적 컴포넌트·`export … from` 재내보내기를 놓친다("읽지 못함"으로 표시). Tailwind 클래스가 `cn()`·`clsx` 조건식·변수로 만들어지면 문자열 리터럴만 읽는다. 사용자별 저장소 검사·AI 제안 횟수 제한이 없다(서버 설정과 허용 목록으로만 막음).

## 남은 일

- **4c 성능 측정의 나머지**: 지금 측정 문서(`docs/perf/implementation-check.md`)는 실제 확인 때의 서버 로그 숫자(시연 renamed, 파일 11개, 로컬 개발 서버, 1회)다. 결론은 코드 판정 0.2초 이내, 기다림의 대부분은 AI(AI 포함 7.2초 중 6.2초)와 DB(약 0.4초). 남은 것은 **파일 30개 기준으로 5회 이상 잰 중앙값·최댓값**과 **화면 체감 시간**(버튼을 누른 뒤 결과가 그려질 때까지)이다.
- 고도화(스펙 `tasks/spec-implementation-check.md`): ① 여러 사람에게 공개하기 전 필수 — 사용자별 저장소 검사·AI 횟수와 동시 실행 제한(DB 기반 카운터, `decideAccess`를 바꾸는 방식) ② 같은 저장소·커밋 결과 캐시 ③ AI 초안 생성(`/api/draft`)의 사용량 제한(지금은 로그인만 확인, ①과 함께) ④ 설계도를 저장소 파일로 다루는 다음 단계에서 확정한 짝 저장과 이름 맞추기 지시.

## 배포

DB 변경은 없다(새 표·마이그레이션 없음). 설정 방법의 원본은 `docs/deploy-checklist.md` 1절·2절.

**환경변수** (모두 서버 전용, `NEXT_PUBLIC_` 접두사 금지)

| 이름 | 필요 | 설명 |
| --- | --- | --- |
| `GITHUB_TOKEN` | 선택(권장) | 공개 저장소만 읽고 Permissions를 하나도 추가하지 않은 fine-grained 토큰. 없으면 GitHub API가 서버 IP당 시간당 60번(저장소 검사 한 번에 2번) |
| `REPO_CHECK_ENABLED` | 저장소 입력을 켤 때 | 정확히 `true`일 때만 켜짐. 없거나 다른 값이면 꺼짐 |
| `REPO_CHECK_ALLOWED_USERS` | 위를 켤 때 | 허용할 GitHub **숫자 id**, 쉼표 구분. 비어 있으면 켜져도 아무도 못 씀 |
| `AI_SUGGEST_ENABLED` | AI 제안을 켤 때 | 정확히 `true`일 때만 켜짐(OpenAI 비용 발생). AI 초안 생성에는 적용되지 않음 |
| `AI_SUGGEST_ALLOWED_USERS` | 위를 켤 때 | 허용할 GitHub 숫자 id, 쉼표 구분. 저장소 검사 목록과 따로 |
| `OPENAI_API_KEY` | 기존 | 초안 생성과 같은 키를 쓴다 |

- GitHub 숫자 id 확인: `https://api.github.com/users/<로그인 이름>`의 `id`. 로그인 이름은 바뀔 수 있어 숫자 id를 쓴다. 서버는 인증 서버의 identities에서 id를 읽는다(user_metadata는 쓰지 않음).

**Vercel 설정·재배포**

1. Settings → Environment Variables에 위 값을 Production(필요하면 Preview)에 넣는다. 켜지 않을 기능은 넣지 않아도 된다(기본 꺼짐).
2. **값을 넣거나 바꾼 뒤에는 재배포해야 반영된다**: Deployments → 최신 배포의 메뉴 → Redeploy.
3. 함수 실행 시간: 구현 검사 라우트는 `maxDuration` 60초다. 저장소 받기는 최대 20초이고, AI는 "55초 − 그때까지 쓴 시간"과 45초 중 짧은 쪽만 쓰도록 맞췄다. Settings → Functions의 최대 실행 시간이 60초 이상인지 확인한다.
4. 처음 공개할 때는 두 기능을 끈 채로 배포하고, 허용 목록에 본인 id만 넣어 켜서 확인한 뒤 넓히는 것을 권한다(사용자별 횟수 제한이 아직 없음).
