# 지시서 생성·내보내기: 계획 (2026-10-31, 11-01 조정)

> **이 문서는**: 설계도를 AI 코딩 에이전트에게 줄 문서(지시서)로 바꿔 복사·내려받게 하는 기능의 작업 계획이다.
> **목록에 들어 있는 것**: 단계 표의 `1`~`7`은 작업 단계다. 보완 칸의 `A`·`B`·`C`는 단계에 덧붙인 보완 작업이다. `NX-05`는 구조 검사 규칙 번호다. 맨 아래에는 이번 범위 밖 목록(고도화)과 알려진 한계가 있다.

화면 하나의 설계도를 AI 코딩 에이전트용 문서로 바꿔 복사·내려받는다. 템플릿만 쓰고 OpenAI를 호출하지 않는다. 같은 입력이면 같은 출력이다.

## 두 문서의 역할 분리

이 화면 하나의 규칙을 프로젝트 루트 CLAUDE.md에 넣으면 다른 작업에도 적용되고 화면끼리 충돌한다. 그래서 "무엇을"은 화면 규칙 파일, "어떻게"는 지시서가 맡고 겹치는 내용은 지시서에서 뺀다.

- **화면 규칙 파일(.claude/rules/<화면>.md)**(`claude_md`, 내려받기 `product-detail.md`): 맨 위 `paths` 머리말(노드 폴더, Next.js + FSD는 `src/` 기준, 라우팅 파일, 정렬·중복 제거; 라우트의 `[id]`는 glob 오해를 피하려고 `*`)과 우선순위, 화면 개요, 규칙(스펙 5항목·스택 규칙·정의가 필요한 토큰·Tailwind 토큰 대응표), 금지 사항, 상태 소유 요약, 컴포넌트 구조, 파일 위치, 배치, 스타일, 확인이 필요한 값.
- **지시서**(`prompt`, 내려받기 `product-detail-prompt.md`): 작업 목표, 참조할 규칙 파일의 실제 경로, 구현 전 확인(미해결 위반 포함), 구현 순서(FSD는 아래 계층부터, 그 외는 말단부터), 구현 원칙(로딩·오류 같은 예외 상태는 "설계에 없는 상태 추가 금지"의 예외), 검증(공통 예외 상태 포함), 완료 보고.
- 지시서 탭 안내: "이 파일을 프로젝트의 `.claude/rules/` 폴더에 넣으세요."
- 프로젝트 전체 공통 지시서는 범위 밖이다.

## 스택별 문장 (core/adapters/*/prompt.ts)

스택(프레임워크·스타일·폴더 구조)에 따라 지시서에 들어가는 문장이 달라진다. 그 문장을 어댑터 파일이 맡는다.

- Tailwind는 스택에 버전을 두지 않고 문장으로 대응한다(4면 `@theme`, 3이면 `theme.extend`). 스펙·설계도의 토큰을 클래스로 바꾸는 대응표를 넣고, 간격은 기본 단위(4px) 가정을 밝힌다. 노드마다 한 줄(배치·자리·스타일 클래스)로 보여 주고 "모듈 스타일" 표기는 쓰지 않는다.
- 스택이 Tailwind인데 노드 스타일 범위가 module이면 utility로 자동 보정하고 보정 내역에 기록한다(`normalizeBlueprint`).
- 검사 규칙 NX-05(경고): FSD가 아닌 Next.js에서 파일 위치가 `pages/`·`app/`으로 시작.

## 단계

아래 표의 "단계"는 번호 순서대로 만든다. "보완"은 그 단계에 함께 하는 추가 작업이다. `drain()`은 저장 큐에 남은 저장 요청을 모두 보내고 기다리는 함수다.

| 단계 | 내용 | 보완 |
|---|---|---|
| 1 | 저장 큐 `drain()` (완료, `7ee7229`) | |
| 2 | 두 문서 생성기(`core/prompt/*`) + 어댑터 문장 + NX-05 + Tailwind 자동 보정 + 기준 파일 + 테스트 (구현 완료, 기준 파일 검토 대기) | C(미리보기 반응형 재사용) |
| 3 | `lib/db/prompt-exports.ts`, 최신 판 조회, **`saveBlueprint`: 최신 판이 지시서와 연결돼 있으면 갱신하지 않고 새 판 추가**(테스트), **스펙 입력의 화면 주소 저장 함수**(테스트) | **A 전체**(4단계 전에 끝낸다), **B의 DB 함수** |
| 4 | 내보내기 라우트 `POST /api/projects/[id]/exports`, 순서 테스트(`drain` → 지시서 저장 → 새 판), 같은 내용 건너뛰기, 변이 실험 | A 규칙을 변이 실험에 포함 |
| 5 | 지시서 탭 화면, 화면 주소 입력과 저장 호출, 복사·내려받기, 경고 띠, 확인 창, "(준비 중)" 제거 | **B의 화면** |
| 6 | 문서 갱신(`CLAUDE.md`, `data-model.md`, 개발 일지) | |
| 7 | `.claude/settings.json`에 셸 명령에 `<<`가 있으면 실행 전에 막는 훅 추가 | 지시서 작업이 끝난 뒤 |

## 지시서 탭 안내 문구 (5단계에 반영)

- 화면 규칙 파일: "이 파일을 프로젝트의 `.claude/rules/` 폴더에 넣으세요."
- 같은 내용 안내: "복사와 내려받기는 같은 내용이어도 몇 번이든 할 수 있습니다. 같은 내용이면 건너뛰는 것은 지시서 기록 저장과 새 판 만들기뿐입니다."

- 지시서 탭 안내(고정 문구 하나만): "새 프로젝트면 공통 규칙은 별도로 정하고, 기존 프로젝트면 기존 CLAUDE.md가 우선입니다."

## 고도화 목록 (이번 범위 밖, 나중에 더 좋게 만들 때 할 일)

- 프로젝트 공통 규칙 파일(프로젝트 전체 지시서).
- 프로젝트 안의 여러 화면(화면 규칙 파일을 화면마다 따로 내려받아 `.claude/rules/`에 모으는 흐름).
- 변경분 지시서(이미 구현된 화면에서 바뀐 부분만 지시).
- 에이전트가 만든 코드 검토(설계도와 실제 코드 비교).
- 이 프로젝트의 스택으로 새 화면 시작.
- 스펙에 "인터랙션·예외 상태" 항목 추가. 지금은 규칙 파일에 기준이 있으면 따르고, 없으면 임의로 구현하지 않고 확인 사항·완료 보고에 기록하게 한다.
- "서버 통신이 아니오인데 책임에 요청 관련 표현이 있는 훅"에 대한 정보 알림(검사 규칙 후보).
- 설계도의 서버 통신을 조회·변경 요청으로 분리. 지금은 `dataFetch` 하나이고 구체적인 내용은 책임에 적는다.
- 프로젝트 스택에 Tailwind 버전(3·4) 선택 추가. 지금은 지시서 문장으로 대응한다.
- 토큰 대응표를 CSS 속성별로 정밀화(지금은 카테고리별 일반 대응과 속성·분류가 맞는 토큰만 클래스로 변환).
- 지시서 추가 메모 칸(사용자가 화면별 메모를 적어 지시서에 넣기).
- HTML·CSS에 맞는 블록·클래스 중심 설계(지금 HTML은 실험적이고 전용 검사 규칙·지시서 문장이 제한적이다. BEM 같은 명명과 블록 단위 구조를 설계도와 지시서에 반영).
- AI로 지시서 다듬기, 지시서 목록·이력 화면. (디자인 시스템 정리 계획에서 지시서 만들기는 최소 버전에서 구현됨: 저장하지 않는 정리 지시서)

### 기능 B(디자인 시스템 정리) 고도화

기능 B는 디자인 시스템 스펙과 현재 컴포넌트 코드를 비교해 합치기·분리를 제안하는 기능이다. 아래는 그 기능을 더 좋게 만들 때의 후보다.

- **공식 컴포넌트 대신 HTML 요소에 직접 스타일을 준 경우 검사**: 공식 `Button`이 있는데 `<button className=…>`을 직접 쓰고 스타일을 주는 사용처를 찾는다(요소별 대응 공식 컴포넌트 목록이 필요).
- **토큰 대신 직접 쓴 값 검사**: 공식 토큰이 있는 색·간격·모서리를 하드코딩(`#2563EB`, `16px`, Tailwind 임의값)한 곳. 스펙의 `tokens`와 값을 맞춰 어떤 토큰으로 바꿀지 제안한다.
- **variant 오용 검사**: 공식 컴포넌트를 쓰면서 공식에 없는 variant 값을 넘기거나, variant 대신 className으로 모양을 바꾸는 사용처.
- 공식 컴포넌트와 같은 이름이지만 props·variants가 다른 경우(드리프트) 검사.
- 완전한 타입 검사기(program) 기반 분석: `@/` 경로 별칭, `export … from` 재내보내기, 패키지 타입까지 따라가 props를 더 정확히 읽는다(지금은 올린 파일 사이의 상대 경로 import만 따라가고 못 읽은 개수만 요약).
- 공개 GitHub 저장소 주소 입력(최소 버전 6단계, 미구현): 지정 폴더의 `.tsx`를 가져와 같은 분석. 비공개 저장소·추가 권한 없음, 파일 수·크기 상한과 요청 제한 안내.
- 정리 결과·지시서의 DB 저장(`prompt_exports.source_type = 'cleanup'`은 표에 이미 있음), AI 설명(F-008), 코드 자동 수정.

## 알려진 한계 (3~4단계, 지금은 처리하지 않는 문제)

- 경쟁 상태(같은 시각에 요청 둘이 겹치는 경우)는 처리하지 않는다: `saveSpecRoute`(행이 없을 때 동시 호출 시 한쪽이 unique 위반으로 실패), `saveBlueprint`(지시서 연결 확인과 쓰기 사이에 지시서가 저장되는 경우), 내보내기(같은 내용 비교와 기록 사이에 같은 요청이 겹치면 같은 기록이 둘 생길 수 있음).
- `prompt_exports`의 RLS 동작은 5단계 화면에서 실제로 내보낼 때 확인한다(지금까지는 가짜 DB 테스트만).
