# 지시서 생성·내보내기: 계획 (2026-10-31, 11-01 조정)

화면 하나의 설계도를 AI 코딩 에이전트용 문서로 바꿔 복사·내려받는다. 템플릿만 쓰고 OpenAI를 호출하지 않는다. 같은 입력이면 같은 출력이다.

## 두 문서의 역할 분리

이 화면 하나의 규칙을 프로젝트 루트 CLAUDE.md에 넣으면 다른 작업에도 적용되고 화면끼리 충돌한다. 그래서 "무엇을"은 화면 규칙 파일, "어떻게"는 지시서가 맡고 겹치는 내용은 지시서에서 뺀다.

- **화면 규칙 파일(.claude/rules/<화면>.md)**(`claude_md`, 내려받기 `product-detail.md`): 맨 위 `paths` 머리말(노드 폴더, Next.js + FSD는 `src/` 기준, 라우팅 파일, 정렬·중복 제거; 라우트의 `[id]`는 glob 오해를 피하려고 `*`)과 우선순위, 화면 개요, 규칙(스펙 5항목·스택 규칙·정의가 필요한 토큰·Tailwind 토큰 대응표), 금지 사항, 상태 소유 요약, 컴포넌트 구조, 파일 위치, 배치, 스타일, 확인이 필요한 값.
- **지시서**(`prompt`, 내려받기 `product-detail-prompt.md`): 작업 목표, 참조할 규칙 파일의 실제 경로, 구현 전 확인(미해결 위반 포함), 구현 순서(FSD는 아래 계층부터, 그 외는 말단부터), 구현 원칙(로딩·오류 같은 예외 상태는 "설계에 없는 상태 추가 금지"의 예외), 검증(공통 예외 상태 포함), 완료 보고.
- 지시서 탭 안내: "이 파일을 프로젝트의 `.claude/rules/` 폴더에 넣으세요."
- 프로젝트 전체 공통 지시서는 범위 밖이다.

## 스택별 문장 (core/adapters/*/prompt.ts)

- Tailwind는 스택에 버전을 두지 않고 문장으로 대응한다(4면 `@theme`, 3이면 `theme.extend`). 스펙·설계도의 토큰을 클래스로 바꾸는 대응표를 넣고, 간격은 기본 단위(4px) 가정을 밝힌다. 노드마다 한 줄(배치·자리·스타일 클래스)로 보여 주고 "모듈 스타일" 표기는 쓰지 않는다.
- 스택이 Tailwind인데 노드 스타일 범위가 module이면 utility로 자동 보정하고 보정 내역에 기록한다(`normalizeBlueprint`).
- 검사 규칙 NX-05(경고): FSD가 아닌 Next.js에서 파일 위치가 `pages/`·`app/`으로 시작.

## 지시서 탭 안내 문구 (5단계에 반영)

- 화면 규칙 파일: "이 파일을 프로젝트의 `.claude/rules/` 폴더에 넣으세요."
- 같은 내용 안내: "복사와 내려받기는 같은 내용이어도 몇 번이든 할 수 있습니다. 같은 내용이면 건너뛰는 것은 지시서 기록 저장과 새 판 만들기뿐입니다."

- 지시서 탭 안내(고정 문구 하나만): "새 프로젝트면 공통 규칙은 별도로 정하고, 기존 프로젝트면 기존 CLAUDE.md가 우선입니다."

## 고도화 목록 (이번 범위 밖)

- 프로젝트 공통 규칙 파일(프로젝트 전체 지시서).
- 프로젝트 안의 여러 화면(화면 규칙 파일을 화면마다 따로 내려받아 `.claude/rules/`에 모으는 흐름).
- 변경분 지시서(이미 구현된 화면에서 바뀐 부분만 지시).
- 에이전트가 만든 코드 검토(설계도와 실제 코드 비교).
- 이 프로젝트의 스택으로 새 화면 시작.
- 스펙에 "인터랙션·예외 상태" 항목 추가. 지금은 규칙 파일에 기준이 있으면 따르고, 없으면 임의로 구현하지 않고 확인 사항·완료 보고에 기록하게 한다.
- "서버 통신이 아니오인데 책임에 요청 관련 표현이 있는 훅"에 대한 정보 알림(검사 규칙 후보).
- 설계도의 서버 통신을 조회·변경 요청으로 분리. 지금은 `dataFetch` 하나이고 구체적인 내용은 책임에 적는다.
- 프로젝트 스택에 Tailwind 버전(3·4) 선택 추가. 지금은 지시서 문장으로 대응한다.
- 토큰 대응표를 CSS 속성별로 정밀화(지금은 카테고리별 일반 대응과 속성·분류가 맞는 토큰만 클래스로 변환).
- 지시서 추가 메모 칸(사용자가 화면별 메모를 적어 지시서에 넣기).
- HTML·CSS에 맞는 블록·클래스 중심 설계(지금 HTML은 실험적이고 전용 검사 규칙·지시서 문장이 제한적이다. BEM 같은 명명과 블록 단위 구조를 설계도와 지시서에 반영).
- AI로 지시서 다듬기, 디자인 시스템 정리 계획에서 지시서 만들기, 지시서 목록·이력 화면.

## 알려진 한계 (3~4단계)

- 경쟁 상태는 처리하지 않는다: `saveSpecRoute`(행이 없을 때 동시 호출 시 한쪽이 unique 위반으로 실패), `saveBlueprint`(지시서 연결 확인과 쓰기 사이에 지시서가 저장되는 경우), 내보내기(같은 내용 비교와 기록 사이에 같은 요청이 겹치면 같은 기록이 둘 생길 수 있음).
- `prompt_exports`의 RLS 동작은 5단계 화면에서 실제로 내보낼 때 확인한다(지금까지는 가짜 DB 테스트만).
